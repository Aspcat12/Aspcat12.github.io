## 3. ปัญหาและแรงจูงใจ (§1–§2)

### 3.1 ข้ออ้างตั้งต้น
- **ข้อ 1 (ข้อมูล):** ชุดข้อมูลเต้น 3D เล็กเกินไป → ครอบคลุมสไตล์เพลงแคบ → generalise แย่
- **ข้อ 2 (การแทนค่า):** วิธีที่มีอยู่ *"either directly regress motion in a continuous space or treat music as a continuous conditioning signal"* → ทำให้การจับ rhythmic cue ละเอียดอ่อนแอ
- **ข้อ 3 (แกนหลักของเปเปอร์):** *"While music appears infinitely diverse from a listener's perspective, from a choreographic standpoint it can be abstracted into a finite set of composable elements [25, 27]"* — ระดับ acoustic = rhythmic primitive จำกัด (2/4, 3/4, 4/4); ระดับ semantic = style category จำกัด (Popping, Jazz, Hip-hop) → ข้อมูลเพลงที่เกี่ยวกับการออกแบบท่า **อยู่บน manifold มิติต่ำ** → **discretise ได้โดยไม่เสียอะไรสำคัญ**

> **⚠️ หมายเหตุสำคัญ:** ข้อ 3 อ้าง **[25] Mason (2012) *Research in Dance Education*** และ **[27] Mitchell & Gallaher (2001) *Music Perception*** ซึ่งเป็นงานฝั่ง **choreomusicology / จิตวิทยาดนตรี** ไม่ใช่งานเชิงปริมาณที่พิสูจน์ว่า manifold มิติต่ำจริง → **นี่เป็นข้ออ้างเชิงแนวคิดที่ยืมความน่าเชื่อถือจาก reference มนุษยศาสตร์ ไม่ใช่ข้ออ้างที่มีหลักฐานเชิงตัวเลข** และเปเปอร์ไม่เคยวัดมิติของ manifold นั้นเลย

### 3.2 Related work — 2 กลุ่ม
- **One-stage** (§2.1): regress motion ต่อเนื่องจาก audio โดยตรง — encoder-decoder [4,14,15,18,30] → GCN [6,34] → GAN [3,12,36] → Diffusion [19–21,31,40,41]. **จุดอ่อนที่เขาชี้:** accumulated error + manifold drift โดยเฉพาะลำดับยาว + diffusion แพง
- **Two-stage** (§2.2): สร้าง choreographic unit ก่อน แล้วเรียน distribution ที่ conditioned บนเพลง — uniform segmentation [1,3,13,42] → VQ-VAE [8] → **แยก codebook บน/ล่าง [28,29] ขยาย capacity จาก L เป็น L×L** → **FSQ [38,39]** + kinematic/dynamic constraint [39]. Backbone: GRU [3] → RNN [12] → Transformer [28,29] → genre conditioning [19,21,49] → pretrained motion model [8,11]

> 🚨 **ย่อหน้า "However, mainstream 3D dance datasets remain limited in scale... reduced expressiveness and realism" ปรากฏซ้ำเกือบคำต่อคำ 2 ครั้ง** — ครั้งแรกใน §1 (หน้า 1) ครั้งที่สองปิดท้าย §2.2 (หน้า 3) **ต่างกันเฉพาะวลี "as illustrated in Fig. 1," ที่มีเฉพาะในครั้งแรก** เป็นสัญญาณของการเขียนเร่ง

## 4. Stage 1 — Dual-Modality Tokenization (§3.3)

### 4.1 Problem setup (§3.1)
- input: genre label `g` (one-hot) + music sequence `M = {m₀…m_T}`, `mₜ ∈ ℝ³⁵` (Librosa)
- output: dance `D = {d₀…d_T}`, `dₜ ∈ ℝ¹⁴⁷` = `[τ; θ]` โดย τ = root translation + θ = 6D rotation [47] ของ SMPL [23]
  → **อนุมานได้ว่า 24 joint × 6 + 3 = 147** ⚠️ **แต่เปเปอร์ไม่เคยระบุคำว่า "24 joints" — นี่คือการอนุมานจากธรรมเนียม SMPL ไม่ใช่สิ่งที่เปเปอร์บอก**
- 🚨 **bug การอ้างอิง:** *"Each mₜ ∈ ℝ³⁵ is extracted with Librosa **[21]**"* — **[21] = Lodge (Li et al. CVPR 2024)** ไม่ใช่ Librosa. ที่อื่นในเปเปอร์อ้าง Librosa เป็น **[18]** (AI Choreographer) ถูกต้องกว่า
- 🚨 **สัญลักษณ์สลับ:** ประโยคเดียวกันนิยาม `dₜ` แล้วเรียกมันว่า `sₜ` ทันที (*"Each dance feature dt ∈ ℝ147 is represented as st = [τ; θ]"*)

### 4.2 FSQ (§3.3.1)
สมการ (1): `ẑ = f(z) + sg[Round(f(z)) − f(z)]` โดย `f(·)` = bounding function (เช่น sigmoid), `sg` = stop-gradient

- **codebook size `k = ∏ᵢ₌₁ᵈ Lᵢ`** · implementation: `ẑ ∈ {8,5,5,5}`, `d = 4` → **k = 8×5×5×5 = 1000 ✓**
- training stage 1: **240 เฟรม/ลำดับ, 200 epochs, Adam (β₁=0.5, β₂=0.99), batch 32**
- เหตุผลที่เลือก FSQ แทน VQ-VAE: *"VQ-VAE often suffers from codebook collapse and uneven code usage"*

> 🚨 **overstatement:** เปเปอร์เขียนว่า FSQ *"guarantees balanced code utilization **by construction**, effectively **eliminating** codebook collapse"* — **แรงกว่าที่ A1-19 (Mentzer et al., FSQ, ICLR 2024) เคลมจริง.** ในสรุป `2309.15505v2.summary.md` ของเราเอง FSQ รายงาน **Codebook Usage เป็นตัวเลขเชิงประจักษ์ (สัดส่วน codeword ที่ถูกใช้อย่างน้อย 1 ครั้ง) ไม่ใช่การรับประกันเชิงโครงสร้าง** และที่ codebook เล็ก **VQ ชนะ FSQ นิดหน่อย**
> → **และ TokenDance เองไม่รายงาน codebook usage ของตัวเองเลยแม้แต่ตัวเดียว** ทั้งที่นี่คือเหตุผลเดียวที่เลือก FSQ

> **⚠️ ความคลุมเครือ:** ประโยค "In our implementation, we set ẑ ∈ {8,5,5,5}... k = 1000" อยู่ใน §3.3.1 (FSQ ทั่วไป) → **ไม่ระบุชัดว่า codebook ทั้ง 4 ตัว (upper, lower, acoustic, semantic) ใช้ค่าเดียวกันหมดหรือไม่** ต้องเดาว่าใช่

### 4.3 Dance Tokenization (§3.3.2)
- **แยก upper/lower body คนละ codebook** — เหตุผล: บน/ล่างมี temporal pattern และความเป็นอิสระต่อกันต่างกัน → แยกแล้ว recombine ได้ยืดหยุ่นกว่า → เพิ่มความหลากหลาย
- **Dance Encoder `E_d`:** 3-layer 1D-CNN → 2-layer MLP · **Dance Decoder `D_d`:** 2-layer MLP → 3-layer 1D transposed conv
- ⭐ **Eq. (2) Dynamic-Kinematic Constraint** — reconstruction objective 6 พจน์:

```
L_d = L_rec(D̂, D)  + L_rec(FK(D̂), FK(D))
    + L_vel(D̂, D)  + L_vel(FK(D̂), FK(D))
    + L_acc(D̂, D)  + L_acc(FK(D̂), FK(D))
```
โดย vel/acc = อนุพันธ์เชิงเวลาอันดับ 1 และ 2, `FK(·)` = forward kinematics [23]
→ บังคับความสอดคล้องของ **ตำแหน่ง + ความเร็ว + ความเร่ง** ทั้งใน **joint space** และ **FK space** พร้อมกัน

> **ไม่มีการระบุน้ำหนัก (λ) ของแต่ละพจน์เลย** — สมการเขียนเป็นผลบวกล้วน แปลว่าน้ำหนัก 1 เท่ากันหมด ซึ่งผิดปกติสำหรับ loss ที่ผสม position/velocity/acceleration ที่มีสเกลต่างกันเป็นสิบเท่า → **ถ้าจะ reimplement ต้องถือว่าข้อมูลไม่ครบ**
> **ไม่ระบุว่า `L_rec`, `L_vel`, `L_acc` เป็น L1 หรือ L2**

### 4.4 Music Tokenization (§3.3.3) — contribution หลัก
- **แยก 35 มิติ Librosa เป็น:** **semantic = MFCC 20 มิติ** · **acoustic = ที่เหลือ 15 มิติ** (20+15 = 35 ✓)
- ให้ **คนละ FSQ codebook** → ขยาย expressive capacity จาก **O(L) → O(L²)** (ตรรกะเดียวกับ upper/lower ของ Bailando)
- **Eq. (3):** `L_m = L_rec(M̂ᵃ, Mᵃ) + L_rec(M̂ˢ, Mˢ)` — reconstruction ล้วน ไม่มี perceptual/adversarial term
- เหตุผลที่ต้องแยก: *"Naively collapsing all musical cues into a single discrete space risks entangling heterogeneous factors that operate at different abstraction levels"*

> 🚨 **การแบ่ง "MFCC = semantic, ที่เหลือ = acoustic" ไม่มีเหตุผลรองรับใด ๆ ในเปเปอร์** — MFCC เป็น timbral/spectral feature ซึ่งตำราสาย MIR มักจัดเป็น *acoustic* มากกว่า *semantic*; ส่วน 15 มิติที่เหลือของ Librosa feature มาตรฐานของ AIST++ คือ chroma + one-hot peak + one-hot beat + envelope ซึ่งเป็นตัวที่**แบก rhythm/harmony** ตรง ๆ. **การตั้งชื่อนี้กลับด้านกับสัญชาตญาณ และเปเปอร์ไม่เคยอธิบาย** → เวลาจะอ้าง ให้อ้างว่า "แยก MFCC ออกจาก feature ที่เหลือ" ไม่ใช่ "แยก semantic ออกจาก acoustic"

## 5. Stage 2 — Local-Global-Local Token-to-Token Generation (§3.4)

### 5.1 สถาปัตยกรรม (Fig. 2)
| ชั้น | ส่วนประกอบ | หน้าที่ |
|---|---|---|
| **Local (in)** | **Music Local Scanner — 2 layer** | Acoustic BiMamba + Semantic BiMamba แยกกัน → จับ dependency ภายในโมดัล (rhythmic/structural cue ระยะสั้น) |
| **Global** | **Global Scanner — 4 layer** | Fusion → Global BiMamba → **genre-aware gating mechanism** (conditioned บน genre embedding) → บังคับความสม่ำเสมอของสไตล์ตลอดลำดับยาว |
| **Local (out)** | **Dance Local Scanner — 2 layer** | แตกเป็น Upper BiMamba + Lower BiMamba → classification head แยกกัน ทำนาย motion token |

- **Hyperparameters:** Mamba block — model dim **512**, state size **16**, conv kernel **4**, expansion factor **2**
- **Training stage 2:** Adam (β₁=0.9, β₂=0.99), **240 เฟรม, 100 epochs, batch 64**, **cross-entropy loss** บน dance token (ตาม [28, 39])
- 🚨 **Fig. 2 มีกล่อง "Repetition" คั่นระหว่าง Global BiMamba กับ Dance Local Scanner ซึ่งไม่ถูกกล่าวถึงที่ใดในเนื้อความเลย** — และมันคือร่องรอยเดียวในเปเปอร์ทั้งฉบับที่บอกใบ้ว่า **อัตรา token ของเพลงกับจำนวนเฟรมของท่าเต้นถูกทำให้ตรงกันอย่างไร** (ดู §7.3)

### 5.2 ทำไม Mamba (§3.4.2)
- **High-Quality:** Transformer เป็น position-invariant ต้องพึ่ง positional encoding → จับ local continuity ละเอียดได้ไม่ดี ขณะที่ music-to-dance ต้องพึ่ง local temporal consistency หนัก · Mamba มี sequential inductive bias ในตัว [7, 33]
- **High-Efficiency:** parallel scan → **non-autoregressive** → ไม่ต้อง decode ทีละ step → เร็วและ scale ได้
- **สมการ (4):** `hₜ = Āₜhₜ₋₁ + B̄ₜxₜ`, `yₜ = Cₜhₜ` โดย `Āₜ, B̄ₜ, Cₜ` ถูก predict แบบ dynamic ผ่าน fully-connected layer (selection mechanism S6 [9] ที่ต่างจาก S4 [10] ซึ่ง A,B,C,Δ คงที่)
- **สมการ (5) discretization:** `Ā = exp(ΔA)`, `B̄ = (ΔA)⁻¹(exp(ΔA) − I)·ΔB`

### 5.3 Bidirectional Mamba (§3.4.3)
- เหตุผล: dependency ใน music-to-dance เป็น **สองทิศทางโดยธรรมชาติ** — musical phrasing พึ่งทั้งบริบทก่อนหน้าและ beat ที่กำลังจะมา ส่วน choreographic continuity ต้อง "คาดการณ์" ท่าถัดไปเพื่อให้ transition เนียน
- กลไก: forward pathway + reversed pathway (กลับลำดับ → ประมวลผล → กลับคืน) → **รวมด้วย element-wise addition** → refine ด้วย **multiplicative skip connection**

> **⚠️ ผลพวงที่เปเปอร์ไม่พูดถึง: BiMamba + non-autoregressive = โมเดลนี้ทำ streaming/online generation ไม่ได้** ต้องมีเพลงทั้งท่อนก่อนถึงจะเริ่ม generate — ซึ่งขัดกับเหตุผลเรื่อง *"real-time motion synthesis, interactive scenarios"* ที่ยกมาเองใน §3.4.2

## 7. สมมติฐานและข้อจำกัด

### 7.1 ที่เปเปอร์ยอมรับเอง (ให้เครดิต)
- §1: FSQ และ BiMamba **ยืมมาจากงานก่อน** ไม่ใช่ของใหม่ (ซื่อสัตย์ผิดปกติ)
- §4.2.1: FIDg บน AIST++ แพ้ Bailando · Lodge ชนะ FIDk และ BAS บน FineDance · POPDG ชนะ DIVk และ BAS บน PopDanceSet
- §4.6: unidirectional Mamba ได้ FIDk ดีกว่าเล็กน้อย
- **การใส่ตัวหนาในตารางถูกต้องตามคอลัมน์ทุกตาราง รวมถึงใส่ให้แถวที่ชนะตัวเอง 2 แถว**
- §5: *"Future work will extend the framework with larger and more diverse datasets, as well as text-based conditioning"*

### 7.2 สมมติฐานที่ไม่ได้ประกาศ (จาก pass 3)
1. **"ข้อมูลเพลงที่เกี่ยวกับการออกแบบท่าอยู่บน manifold มิติต่ำ"** — เป็นแกนของทั้งเปเปอร์ แต่**ไม่เคยวัด** (ไม่มี intrinsic dimension, ไม่มี codebook usage, ไม่มี reconstruction bound ที่เชื่อมกับ downstream)
2. **MFCC = semantic** — ไม่มีเหตุผลรองรับ และสวนทางกับธรรมเนียม MIR (ดู §4.4)
3. **codebook ทั้ง 4 ตัวใช้ config {8,5,5,5} เหมือนกัน** — เดาจากตำแหน่งย่อหน้า
4. **`dₜ ∈ ℝ¹⁴⁷` = 24 joint × 6 + 3** — เปเปอร์ไม่เคยบอกจำนวน joint
5. **baseline ทั้งหมดถูกเทรนใหม่บนแต่ละชุดข้อมูลด้วยโปรโตคอลเดียวกัน** — ไม่มีประโยคใดยืนยัน → **ที่มาของตัวเลข baseline ไม่ชัด** (คัดลอกมา หรือรันเอง?)
6. **การรวม forward/backward ด้วย element-wise addition + multiplicative skip** — ไม่มี ablation ว่าทำไมไม่ concat
7. **น้ำหนักของ 6 พจน์ใน Eq. (2) = 1 เท่ากันหมด** — ไม่น่าจะจริงในทางปฏิบัติ
8. **Table 9 ใช้ FineDance** — อนุมานจากตัวเลข ไม่ใช่จาก caption

### 7.3 ข้อจำกัดเชิงปฏิบัติ (ถ้าจะ reimplement)
- ไม่มีโค้ด ไม่มี checkpoint ไม่มี project page
- **ไม่มี downsample factor และไม่อธิบายกล่อง "Repetition" ใน Fig. 2** → ไม่รู้ token rate → คำนวณ bitrate ไม่ได้ และไม่รู้ว่า music token กับ dance frame ถูกจับคู่กันอย่างไร
- ไม่มีน้ำหนัก loss, ไม่มี learning rate, ไม่มี scheduler, ไม่มี normalization scheme
- ไม่มีสูตร FIDk/FIDg/DIVk/DIVg/BAS (อ้าง [18, 28, 29] ลอย ๆ)
- **non-autoregressive + bidirectional → ทำ streaming ไม่ได้** (ขัดกับ motivation "real-time" ของตัวเอง)

### 9.1 ตำแหน่งในคลัง — checklist ข้อ 20 "ขั้ว token ฝั่งตรงข้าม + FSQ/factorized codebook"
เปเปอร์นี้ปิดข้อ 20 ให้ครบ (คู่กับ `2604.00927` Dance Fingerprinting และ `2604.18648` DanceCrafter) และมัน**ต่างจาก DanceCrafter คนละขั้ว**:

|---|---|---|---|
| การแทนค่า | continuous (flow matching) | **discrete token (FSQ)** | **discrete token (k-means)** |
| ที่มาของ vocabulary | มนุษย์ประกาศ (Laban/Vaganova) | **เรียนจากข้อมูล (FSQ, k=1000)** | **ค้นพบด้วย clustering (V=216/362)** |

| conditioning | ข้อความละเอียด | **เพลง (token) + genre** | **unconditional** |
| backbone | DiT | **BiMamba (non-AR)** | **LSTM (AR)** |

### 9.2 ผลต่อ thesis claims ของเรา
- **T4 (codebook collapse):** เปเปอร์นี้ **หนุนข้อสรุปเดิมของเราจาก A1-19** ว่า FSQ เป็นคำตอบของ collapse — แต่ **เปเปอร์นี้ *ไม่ใช่* หลักฐานเพิ่ม** เพราะไม่รายงาน usage เลย (มันแค่ *อ้าง* A1-19 ต่อ แถมแรงเกินต้นฉบับ) → **อย่าใช้ TokenDance เป็น citation สำหรับตัวเลข collapse** ให้ใช้ A1-19 โดยตรงเสมอ
- **T1 (vocabulary size vs data):** TokenDance ใช้ **k=1000 บนคลัง 3.56–7.7 ชม.** ขณะที่ A1-17 (Keyposes) ใช้ **k=100 บนคลังเล็ก** และ L3-22 พบว่า **k ≤ 1000 ปลอดภัย** → k=1000 ของ TokenDance นั่งอยู่ที่ขอบบนพอดี และ **ไม่มีการ sweep k เลย** → **ไม่ขัด V=216 ของเรา และไม่หนุนด้วย** (ยังต้องทำ E4 เอง)
- **การแยกร่างกาย:** ให้ **ข้ออ้างเชิงโครงสร้าง** เพิ่มว่า upper/lower factorisation คือคำตอบมาตรฐานต่อ vocabulary blow-up — **แต่ทั้ง TokenDance และ Bailando ไม่เคยวัดว่ามันช่วยเท่าไร** (ไม่มี ablation whole-body vs split ที่ใดเลย) → ยังเป็น **future work direction ไม่ใช่ข้อบังคับ** (ตรงกับที่ `paper_chain.md` บันทึกไว้แล้ว)
- **BAS / conformity metric:** ⭐ ได้หลักฐานใหม่ว่า **BAS สูงกว่า GT ได้ถึง 13.1%** → หนุนคำเตือนของ A1-16 ว่า metric ตระกูล "ความสอดคล้องกับจังหวะ/สไตล์" **ไม่ใช่ quality metric** → ใส่ในบท Evaluation ของเราได้ทันทีคู่กับ A1-16
- **การประเมินแบบไม่มีเฉลย (R11-1 Sturm & Ben-Tal):** TokenDance อยู่ **ระดับ 1 (population statistics) + ระดับ 2 อ่อน ๆ (user study)** และ **ไม่มีระดับ 3 (nefarious tester) เลย** → ยืนยันอีกครั้งว่า **E11 ยังเป็นช่องว่างฟรีในวรรณกรรมสายนี้**

### 9.3 สิ่งที่ *ไม่* ทับกับเรา
- เขาเป็น **music-conditioned** เราเป็น **unconditional** → metric ครึ่งหนึ่งของเขา (BAS และ FID ที่พึ่ง audio pairing) ใช้กับเราไม่ได้
- เขาทำงานบน **SMPL 147 มิติจาก mocap** เราทำบน **MediaPipe 33 landmark จากวิดีโอเดี่ยว** (งบความคลาดเคลื่อน 146 มม. ตาม A1-14) → ตัวเลข FID ของเขาเทียบกับเราไม่ได้เลย
- เขามี 3 ชุดข้อมูล × หลายนักเต้น เรามีนักเต้นคนเดียว → **SinMDM/A1-12 ยังเป็นเปเปอร์ที่ตรงกับข้อจำกัดเราที่สุด ไม่ใช่เปเปอร์นี้**

## 12. บทสรุปในประโยคเดียว

> **TokenDance เป็นหลักฐานปี 2026 ที่ดีที่สุดว่า "สาย token ยังเป็นสถาปัตยกรรมที่มีชีวิต" (ชนะ latency ขาดลอย 1.22 s vs 4.57 s และชนะ FIDk บน in-the-wild dataset ถึง 34.5%) และตารางของมันซื่อสัตย์ผิดปกติ — ใส่ตัวหนาให้คู่แข่งทุกครั้งที่แพ้ รวมถึงสองแถวที่ชนะโมเดลเต็มของตัวเอง — แต่ *ข้อความที่บรรยายตาราง* เชื่อไม่ได้ (blocker 4 จุด: ป้ายชื่อ Full/+MT ขัดกัน, บอกว่าได้ FIDg ต่ำสุดทั้งที่ Bailando ต่ำกว่าและถูกใส่ตัวหนาไว้เอง, เคลม "MT consistently improves" ที่ตารางตัวเองหักล้าง 4 เซลล์, และไม่เทียบกับ MEGADance/MatchDance ซึ่งเป็นงานของผู้แต่งเองที่ใกล้ที่สุด) — และคุณค่าที่แท้จริงของมันสำหรับเราคือ *สิ่งที่มันไม่ทำ*: มันเลือก FSQ เพราะเรื่อง codebook usage แล้วไม่เคยรายงาน usage, เรียน vocabulary ท่าเต้นขึ้นมาแล้วไม่เคยเปิดดูว่าในนั้นมีอะไร — ซึ่งคือช่องว่างที่งานเราอยู่พอดี.**
