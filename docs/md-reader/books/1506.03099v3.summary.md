## ⚠️ อ่านตรงนี้ก่อน — ข้อที่เปลี่ยนวิธีใช้เปเปอร์นี้

1. **เปเปอร์นี้ไม่ได้ใช้คำว่า "exposure bias" และไม่ได้ใช้คำว่า "teacher forcing" เลยสักครั้ง.** ผู้แต่งเรียกปัญหาว่า *"discrepancy between training and inference"* (abstract, §1) · (verifier ค้นคำ "exposure" / "teacher" / "forcing" ใน text ของ PDF = 0 ครั้ง) · คำว่า "exposure bias" มาจากงานหลังจากนี้ (ความรู้ภายนอก — ไม่อยู่ในเปเปอร์นี้, ต้อง verify แหล่งก่อนอ้าง) → **`reading_checklist.md` R11-3 เขียนว่า "ตั้งชื่อให้ปัญหา exposure bias" ไม่ตรงตัวอักษร** · อ้างได้ว่า "ระบุปัญหา train/inference discrepancy" แต่ถ้าจะเขียนคำว่า exposure bias ในวิทยานิพนธ์ต้องอ้างแหล่งที่บัญญัติคำนั้นคู่กัน
2. **เปเปอร์ *ไม่ได้วัด* ว่า error สะสมตามความยาว.** ข้อความ "errors that can accumulate quickly along the generated sequence" (**abstract**, p.1 — ถ้อยคำนี้อยู่ใน abstract เท่านั้น; ใจความเดียวกันถูก paraphrase ใน §1 "mistakes made early … can be quickly amplified", §2.3 "cumulative bad decisions", §5 "prone to the accumulation of errors along the decision paths") เป็น **ข้อโต้แย้งเชิงเหตุผล** ไม่มีกราฟ/ตาราง quality-vs-length เลย · ผลทุกตารางเป็นค่ารวมทั้ง sequence → **ห้ามอ้างเปเปอร์นี้เป็นหลักฐานเชิงประจักษ์ว่า "คุณภาพทรุดตามความยาว rollout"** · สำหรับ E9 (rollout 10/50/120) แบบอย่างเชิงวัดที่อ้างได้คือ `E_T` vs horizon ของ Galata 2001 (A1-21) ไม่ใช่เปเปอร์นี้
3. **Scheduled sampling ไม่ใช่งาน "flag เดียว" สำหรับโค้ดเรา (การประเมินของเรา).** กลไกในเปเปอร์ (§2.4) สุ่มเหรียญ **ต่อ token ที่ป้อนเข้า recurrent state ทีละก้าว** โดยมี loss ทุกก้าว (Eq. 1, 4) · แต่ `src/train_lstm.py:47` ทำนาย **จาก timestep สุดท้ายของหน้าต่างเท่านั้น** (`self.fc(out[:, -1, :])`, docstring บรรทัด 9: `(X: [N, seq_len], y: [N])`) และ `src/generate.py:92-93` ป้อนหน้าต่างเลื่อน `seq[-seq_len:]` ใหม่ทุกก้าว และทิ้ง hidden state (`logits, _ = model(x)`) → การจะใส่ scheduled sampling **ทางหนึ่งคือ** (ก) ให้โมเดลคำนวณ logits ทุกตำแหน่ง (ข) รันสองรอบ: รอบแรกหา prediction ในหน้าต่าง, รอบสองแทนที่ input ด้วย prediction ด้วยความน่าจะเป็น 1−ε_i (ค) เพิ่ม schedule + hyperparameter k · **อีกทางหนึ่ง** คงสถาปัตยกรรมไว้แล้วหา token ทดแทนในหน้าต่างด้วย forward pass เพิ่มบนหน้าต่าง context ก่อนหน้าจาก corpus — ทั้งสองทางเป็นการแก้โค้ดหลายสิบบรรทัด + hyperparameter ใหม่ **ไม่ใช่ flag เดียว**
   **ถ้อยคำในเอกสารโปรเจกต์ที่ควรแก้ (ตรงตัว):** `paper_chain.md:3300-3301` "one-flag **experiment**" · `paper_chain.md:3434` "scheduled sampling is a one-flag fix" · `docs/ADVISOR_METRICS_2026-09.md:157` "scheduled sampling แก้ได้ด้วย flag เดียว" · `memory.txt:744` "One-flag experiment" · `memory.txt:774-775` "scheduled sampling is a one-flag fix" · `paper_index_A.csv:73` "Names exposure bias … One-flag experiment" · `reading_checklist.md:218-219` (E9) "scheduled sampling คือแฟล็กเดียว"
4. **ผลดีขึ้นส่วนหนึ่งอาจเป็นแค่ regularization.** · **Parsing — ผู้แต่งยอมรับเอง:** *"Whether the effect of sampling during training helps with regard to overfitting or the training/inference mismatch is unclear"* (§4.2, p.6) · **Captioning — ผู้แต่งเคลมกลับกัน:** รัน Uniform SS (แทน token ด้วย token สุ่มแบบ uniform ไม่ใช่ของโมเดล) *"to verify … that the performance boost was not just a simple form of regularization"* (§4.1, p.5) เพราะ SS จริงชนะ Uniform SS (30.6 / 92.1 vs 29.2 / 90.9) · **แต่ (การอนุมานของเรา)** Uniform SS **ก็ชนะ baseline** (BLEU-4 29.2 vs 28.8, CIDEr 90.9 vs 89.5) → ส่วนหนึ่งของผลน่าจะเป็น regularization อยู่ดี → ถ้าเราลอง SS บน corpus เล็กแล้วดีขึ้น **ต้องมี control แบบ Uniform SS** ถึงจะเคลมว่าแก้ train/inference mismatch ได้
5. **"Always Sampling" ไม่ได้แย่เสมอ.** แย่มากใน captioning (BLEU-4 11.2) และ parsing (ต้นไม้ไม่ valid, F1 = "-") แต่ใน speech **ดีกว่า baseline ขาด** (decoding FER 35.8 vs 46.0) · ผู้แต่งอธิบายว่า label HMM-state ซ้ำกันหลายเฟรม → baseline พึ่ง label ก่อนหน้ามากเกินไป ไม่พึ่ง acoustic · **ข้อนี้ตรงกับเราโดยตรง:** token ของเราก็ซ้ำ/autocorrelated สูง (ถ้าไม่ dedup) → โมเดลเสี่ยงเรียน "copy token ก่อนหน้า" แบบเดียวกัน (การอนุมานของเรา)
6. **ไม่มีการทดสอบนัยสำคัญ ไม่มี error bar ไม่มีการระบุค่า k ของ schedule.** Abstract เขียน "significant improvements" แต่ไม่มี p-value/SD · captioning และ parsing ไม่บอกจำนวน run · speech เฉลี่ย 3 models ไม่มี SD · **ไม่ระบุค่า k ของ inverse sigmoid ที่ใช้จริง** · **ไม่ระบุวิธี decode ของ captioning และ parsing** (ระบุเฉพาะ speech = beam 10) → reproduce ตรง ๆ ไม่ได้
7. **เปเปอร์ไม่ได้พูดถึง temperature / top-k / top-p.** §2.3 อธิบายทั่วไปว่า token ก่อนหน้าได้จาก "select the most likely one ... or sample according to it" และอธิบาย beam search · วิธี decode ที่ระบุจริงมีเฉพาะ speech (beam 10, §4.3) → **ไม่ช่วยให้เหตุผลกับ `--temperature 0.9`** ยังต้องพึ่ง R11-2 (Holtzman) / E8

## 3. ปัญหาและแรงจูงใจ (§1, §2.1–2.3)

- **โมเดล (Eq. 1–3):** log P(Y|X) = Σ_t log P(y_t | y_1^{t−1}, X) · RNN ประมาณด้วย state h_t โดย h_1 = f(X; θ), h_t = f(h_{t−1}, y_{t−1}; θ) · P(y_t|h_t) = linear projection + softmax (footnote 1: อาจเป็น multi-layer non-linear ก็ได้) · เพิ่ม token `<EOS>` เพื่อรองรับความยาวแปรผัน
- **การเทรน (Eq. 4):** θ* = argmax Σ log P(Y^i | X^i; θ) ด้วย mini-batch SGD — คือ maximum likelihood ที่ป้อน token จริง
- **Inference (§2.3):** สร้างทีละ token · token ก่อนหน้าได้จาก "most likely" หรือ "sample" · ใช้ beam search แบบ heap ขนาด m คืน k sequence ที่ดีที่สุด · beam ใช้กับ RNN ได้ไม่ดีเพราะ state ต่อเนื่อง factor ไม่ได้
- **ปัญหาหลัก:** *"if a wrong decision is taken at time t−1, the model can be in a part of the state space that is very different from those visited from the training distribution"* และนำไปสู่ "cumulative bad decisions" — ผู้แต่งเทียบกับ sequential Gibbs sampling ที่ sample อนาคตไม่มีผลต่ออดีต

## 4. วิธีการ — Scheduled Sampling (§2.4)

- ต่อ mini-batch i และทุก token y_t ที่ต้องทำนาย: ใช้ **y_{t−1} จริง** ด้วยความน่าจะเป็น **ε_i**, ใช้ **ŷ_{t−1} จากโมเดล** ด้วย **1−ε_i**
- ε_i = 1 → เทรนแบบเดิม · ε_i = 0 → เทรนในสภาพเดียวกับ inference ("Always Sampling")
- **เหตุผลของ curriculum:** ต้นการเทรนโมเดลยังแย่ ถ้าสุ่มจากโมเดล = token มั่ว → converge ช้ามาก จึงควรใช้ของจริงก่อน · ท้ายการเทรนควรใช้ของโมเดลบ่อยขึ้นให้เหมือน inference
- **Schedule (Fig. 2):**
  - Linear: ε_i = max(ε, k − c·i), 0 ≤ ε < 1 = "minimum amount of truth"
  - Exponential: ε_i = k^i, k < 1
  - Inverse sigmoid: ε_i = k / (k + exp(i/k)), k ≥ 1
  - (ทุกตัว "k ขึ้นกับความเร็วที่คาดว่าจะ converge" — **ไม่มีค่าที่ใช้จริงสำหรับ captioning/parsing**)
- **Coin ต่อ token ไม่ใช่ต่อ sequence** — footnote 2: ต่อ sequence "much worse" เพราะ error ต่อเนื่องถูกขยายในรอบแรก ๆ · §4.1: ต่อ sequence แย่ "as poor as the Always Sampling approach" (ไม่มีตัวเลข)
- **ไม่ backprop gradient ผ่านการตัดสินใจสุ่ม** — ระบุว่าเป็น future work (§2.4, §5) และ §4.3 ใช้เป็นคำอธิบายว่าทำไม validation accuracy ของโมเดล sampling ตกหลัง ~9 epochs
- **ต้นทุน:** footnote 3 — ไม่ช้าลงหรือเร็วขึ้นอย่างมีนัย; §5 "while not incurring longer training times"

| **Collins & Roark [12]** | ใช้ beam ทั้งตอนเทรนและ inference + ranking loss · ใช้กับ RNN ไม่ได้ดีเพราะ state ต่อเนื่อง factor ไม่ได้ |

## 6. ผลการทดลอง (§4) — ตัวเลขทั้งหมด

### 6.1 Image captioning — MSCOCO (§4.1, Table 1)
**Setup:** train 75k ภาพ, รายงานบน dev 5k ภาพแยก · 5 captions/ภาพ สุ่มหนึ่งตอนเทรน · CNN pretrained (คล้าย [20] batch-norm) ตัด layer สุดท้าย, embedding ภาพเป็น "คำแรก" · LSTM 1 ชั้น 512 hidden, word embedding 512, dictionary **8,857** คำ · schedule = **inverse sigmoid**

| Approach | BLEU-4 | METEOR | CIDEr |
|---|---|---|---|
| Baseline | 28.8 | 24.2 | 89.5 |
| Baseline with Dropout | 28.1 | 23.9 | 87.0 |
| Always Sampling | **11.2** | 15.7 | 49.7 |
| **Scheduled Sampling** | **30.6** | 24.3 | **92.1** |
| Uniform Scheduled Sampling | 29.2 | 24.2 | 90.9 |
| Baseline ensemble of 10 | 30.7 | 25.1 | 95.7 |
| Scheduled Sampling ensemble of 5 | 32.3 | 25.4 | 98.7 |

- SS ชนะ baseline: BLEU-4 +1.8, METEOR +0.1 (แทบเท่า), CIDEr +2.6
- **Dropout ช่วย log-likelihood (ไม่แสดงตัวเลข) แต่แย่ลงบน metric จริง** — สังเกต: likelihood ≠ คุณภาพ output
- Uniform SS > baseline แต่ < SS → ผู้แต่งใช้ยืนยันว่า "ไม่ใช่แค่ regularization" (แต่ก็แสดงว่ามีส่วนที่เป็น regularization อยู่ด้วย — ดู ⚠️ 4)
- ensemble ไม่เท่ากัน (10 vs 5) — SS ensemble 5 ยังชนะ baseline ensemble 10
- ผู้แต่งระบุว่า baseline ของตน "consistent (slightly better) with the current state-of-the-art" (p.5)
- ใช้ในผลงานที่ **อันดับ 1 final leaderboard MSCOCO captioning challenge 2015** [21]
- ⚠️ ไม่มี SD, ไม่บอกจำนวน run, ไม่บอกค่า k

### 6.2 Constituency parsing (§4.2, Table 2)
**Setup:** linearize parse tree เป็น sequence ตาม [4] · LSTM 1 ชั้น 512 cells, embedding 512, attention แบบ [22] · input dictionary ~90k คำ, target dictionary **128** สัญลักษณ์ · **40k training instances** · schedule = inverse sigmoid · รายงาน F1 บน **WSJ 22 dev** [23]
- งานนี้แทบ deterministic: perplexity ทั้ง train และ test ของ parsing ≈ **1.1** เทียบกับ captioning ≈ **7** ("1.1 vs. 7", p.6)

| Approach | F1 |
|---|---|
| Baseline LSTM | 86.54 |
| Baseline LSTM with Dropout | 87.0 |
| Always Sampling | – (ต้นไม้มัก invalid) |
| Scheduled Sampling | 88.08 |
| Scheduled Sampling with Dropout | **88.68** |

- SS +1.54 F1 เหนือ baseline; ผลบวก **additive กับ dropout**
- ⚠️ ผู้แต่งยอมรับ: ข้อมูลน้อย (40k) → overfitting มีผลมาก · **ไม่ชัดว่า SS ช่วยเรื่อง overfitting หรือ train/inference mismatch** ← สำคัญมากสำหรับ corpus เล็กของเรา

### 6.3 Speech recognition — TIMIT (§4.3, Table 3)
**Setup ต่างจากส่วนอื่น:** input/output ยาวเท่ากันและ aligned (Eq. 5–6) · h_1 = f(o_h, S, x_1) โดย o_h = เวกเตอร์ศูนย์, S = token เริ่ม sequence · feature 40-d log Mel filterbank + Δ + ΔΔ · target 180 มิติ = HMM-state label จาก forced alignment (GMM-HMM, Kaldi) · train/val/test = **3,696 / 400 / 192** sequences เฉลี่ย **304 เฟรม** · LSTM **2 ชั้น × 250 cells** + softmax · ε_i ลด **linear** จาก ε_s ไป ε_e ใน 10 epochs แล้วคงที่ · **3 models ต่อ config เฉลี่ย** · เลือก epoch ด้วย validation · decoding: beam **10**

| Approach | ε_s | ε_e | Next Step FER (val) | Decoding FER (test) |
|---|---|---|---|---|
| Always Sampling | 0 | 0 | 34.6 | 35.8 |
| **Scheduled Sampling 1** | 0.25 | 0 | 34.3 | **34.5** |
| Scheduled Sampling 2 | 0.5 | 0 | 34.1 | 35.0 |
| Scheduled Sampling 3 | 0.9 | 0.5 | 19.8 | 42.0 |
| Baseline LSTM | 1 | 1 | **15.0** | 46.0 |

- **รูปแบบที่ควรจำ:** ยิ่งเทรนด้วย ground truth มาก → next-step FER ดีขึ้นอย่างต่อเนื่อง (34.6 → 34.3 → 34.1 → 19.8 → 15.0) · decoding FER **โดยรวมแย่ลงแต่ไม่ต่อเนื่อง** (35.8 → **34.5** → 35.0 → 42.0 → 46.0 — ต่ำสุดคือ SS1 ไม่ใช่ Always Sampling) · คำเคลมของผู้แต่งเองแคบกว่า: *"the models that were trained with sampling perform better than the baseline during decoding"* (p.7)
- baseline ดีที่สุดใน next-step (15.0) แต่แย่ที่สุดใน decoding (46.0) = ต่าง 31 จุด · ⚠️ **ช่องว่างนี้ปน 3 ปัจจัย:** ป้อนของจริง vs ป้อนของตัวเอง, **validation vs test set**, และ **มี beam search vs ไม่มี** (Table 3 caption, p.8) → อย่าอ้าง "31 จุด" ว่าเป็นผลของ feeding mode ล้วน ๆ
- ⟹ ตรงกับ `ADVISOR_METRICS_2026-09.md` §(ข): **perplexity/accuracy แบบ teacher-forced ของเราไม่ได้บอกคุณภาพตอน generate** — เปเปอร์นี้ให้ตัวอย่างตัวเลขจริงของการกลับด้านนี้ (อ้างได้ แต่ระบุว่าเป็นโดเมน speech ที่ label autocorrelated สูง)
- Baseline ถึง best validation ~14 epochs, โมเดล sampling ~9 epochs แล้ว validation accuracy ตก — ผู้แต่งโทษการไม่ backprop ผ่าน sampling
- **Always Sampling ดีเพราะ** HMM state ซ้ำหลายเฟรม + transition จำกัด → โมเดลที่ป้อน groundtruth พึ่ง label history มากเกิน ไม่พึ่ง acoustics · Always Sampling "effectively ignores its own predictions" · ผู้แต่งบอกว่าโมเดลแบบ attention ที่ทำนาย phone ตรง ๆ [26] จะไม่มีปัญหานี้
- ไม่ใช้ HMM decode (ไม่ใช่ hybrid) → **เทียบกับผล TIMIT มาตรฐานไม่ได้** (ผู้แต่งระบุเอง)
- ⚠️ Table 3 caption: "four different linear schedulings" vs เนื้อความ "three scheduled sampling configurations" (+ Always Sampling) — กำกวม (4 ถ้านับ Always Sampling เป็น schedule 0→0) · ไม่มี SD ของ 3 models

## 8. สมมติฐานและข้อจำกัด (pass 3)

**สมมติฐานที่เปเปอร์ต้องการ**
- โมเดลมี **recurrent state ที่รับ token ก่อนหน้าเป็น input ทีละก้าว** และมี loss ทุกตำแหน่ง (Eq. 1–4) — โครงนี้ไม่ตรงกับ window-classifier ของเรา (⚠️ 3)
- โมเดล "ดีพอ" ท้ายการเทรนให้ token ที่สุ่มมาสมเหตุผล — ถ้าโมเดลอ่อน (corpus เล็กแบบเรา) การป้อน token ของตัวเองอาจเป็นแค่ noise ที่ทำตัวเป็น regularizer
- metric ปลายทาง (BLEU/F1/FER-decoding) คือสิ่งที่ต้องการ — ไม่ใช่ likelihood

**จุดอ่อน/ข้อจำกัด**
1. ไม่มี statistical test / SD; captioning และ parsing ไม่บอกจำนวน run → "significant" ใน abstract ไม่ใช่ความหมายทางสถิติ
2. ไม่ระบุค่า k ของ schedule สำหรับ captioning/parsing → reproduce ไม่ได้
3. Gradient ไม่ไหลผ่านการสุ่ม → objective ไม่ใช่ของ "จริง" (ผู้แต่งยอมรับ)
4. ไม่วัด error-vs-length โดยตรง (⚠️ 2)
5. แยกผล "แก้ mismatch" กับ "regularization" ไม่ออกทั้งหมด (⚠️ 4)
6. ผลทุกงานเป็น RNN + discrete token vocabulary 128–8,857 ตัว, ข้อมูล 3.7k–75k ตัวอย่าง — **ใหญ่กว่าเราหลายระดับ** (เรา ~30 segments; vocab 216/362)
7. Ensemble ไม่เท่ากัน (10 vs 5)
8. ความรู้ภายนอก (ไม่อยู่ในเปเปอร์ — ต้อง verify ก่อนอ้าง): มีงานภายหลังวิจารณ์ว่า scheduled sampling ไม่ใช่ objective ที่ consistent ทางทฤษฎี และเสนอทางอื่น (เช่น Professor Forcing) → ถ้าจะใช้ SS ในวิทยานิพนธ์ควรตามอ่านงานวิจารณ์ด้วย

**จุดแข็ง (ใช้หนุนงานเรา)**
- ตัวอย่างตัวเลขว่า **metric แบบป้อนของจริง (next-step) กับแบบป้อนของตัวเอง (decoding) กลับทิศกันได้** (Table 3 — โปรดจำ caveat val/test + beam ใน §6.3) → หนุนการที่เราไม่ควรรายงานแค่ val_acc/perplexity ของ `train_lstm.py`
- Always Sampling เป็น control ราคาถูก, Uniform SS เป็น control สำหรับแยก regularization — ออกแบบการทดลองให้เราได้เลย
- ใช้ง่าย ไม่เพิ่มเวลาเทรน

## 10. ความสัมพันธ์กับงานข้างเคียงและกับโปรเจกต์ของเรา

### 10.1 เทียบกับคลังที่สรุปแล้ว
- **A1-21 Galata 2001 (VLMM):** ให้ `E_T` vs horizon ด้วย Monte-Carlo 50 ครั้ง = วิธีวัดการสะสม error ตามความยาวที่ **เปเปอร์นี้ไม่มี** → E9 ควรอ้าง A1-21 เป็นวิธีวัด และอ้าง A1-27 เป็นเหตุผลว่าทำไมต้องวัด
- **L3-35 folk-rnn / L3-36 Sturm & Ben-Tal:** sampling แบบ multinomial ธรรมดา ไม่พูดถึง mismatch — A1-27 เติมช่องว่างด้านการเทรน
- **R11-2 Holtzman (ยังไม่อ่าน):** ปัญหาฝั่ง *decoding* (likelihood ผิดตอน decode) — คู่กับ A1-27 ที่เป็นปัญหาฝั่ง *training input* · อย่าผสมสองเรื่อง: temperature/top-p ไม่แก้ train/inference mismatch และ SS ไม่แก้ degeneration จาก decoding rule
- **A1-17 Keyposes (GRU ทำนาย keypose ถัดไป):** สถาปัตยกรรมใกล้เรา — ถ้าเขามีวิธีจัดการ mismatch ควรเทียบ (ไม่ได้ตรวจในรอบนี้)

### 10.2 ผลต่อ thesis ของเรา
1. **Methods:** อ้าง A1-27 เพื่ออธิบายว่า `train_lstm.py` เทรนด้วย ground-truth window แต่ `generate.py` ป้อน token ของตัวเอง → train/inference discrepancy (ใช้คำของเปเปอร์) · ถ้าใช้คำว่า exposure bias ให้อ้างแหล่งที่บัญญัติคำ
2. **Evaluation:** Table 3 เป็นหลักฐาน (พร้อม caveat §6.3) ว่า val_acc แบบป้อน window จริง (`train_lstm.py:111-113`) **ไม่พอ** ต้องมี metric บน rollout (E7/E9) · ข้อสังเกตข้างเคียงจาก verifier (ไม่เกี่ยวกับเปเปอร์): `train_lstm.py:80-82` แบ่ง train/val แบบสุ่มระดับ window ซึ่งน่าจะซ้อนทับกัน → val_acc อาจสูงเกินจริงจาก leakage อีกชั้นหนึ่ง
3. **E9 ออกแบบใหม่:** (ก) วัดคุณภาพ vs ความยาว rollout 10/50/120 ก่อน (ข) ถ้าทรุด → ลอง SS **พร้อม control 3 ตัวตามเปเปอร์:** Always Sampling, **Uniform SS** (แยก regularization), dropout (ค) รายงานหลาย seed + SD (สิ่งที่เปเปอร์ไม่ทำ) (ง) ต้องแก้สถาปัตยกรรมให้มี loss ทุกตำแหน่งก่อน — ไม่ใช่ flag เดียว
4. **ความเสี่ยงแบบ speech (⚠️ 5):** ถ้า token sequence ของเรามีการซ้ำติดกันเยอะ โมเดลอาจเรียน "copy ตัวก่อน" → ควรเช็คอัตรา self-transition ใน `transition_matrix.npy` ก่อนตีความผล

### 10.3 จุดแข็ง / จุดอ่อน (สรุป)
- แข็ง: venue A*, แนวคิดง่าย, control ออกแบบดี (Always / Uniform), ตัวเลข Table 3 ชัด
- อ่อน: ไม่มีสถิติ, ไม่มี hyperparameter schedule, ไม่วัด error-vs-length, gradient ไม่ครบ, แยก regularization ไม่ขาด

## บทสรุปในประโยคเดียว
Scheduled Sampling แก้ความไม่ตรงกันระหว่างการเทรน (ป้อน token จริง) กับ inference (ป้อน token ของตัวเอง) ด้วยการสุ่มแทนที่ token จริงด้วย token ของโมเดลในสัดส่วนที่เพิ่มขึ้นตาม schedule — ได้ผลดีขึ้นพอประมาณใน 3 งาน (BLEU-4 28.8→30.6, F1 86.54→88.08, decoding FER 46.0→34.5) แต่ **ไม่ได้วัดการสะสม error ตามความยาว, ไม่มีสถิติ, และแยกออกจาก regularization ไม่ขาด** — สำหรับเรา ใช้เป็นเหตุผลใน Methods และเป็นแม่แบบของ control ใน E9 ได้ แต่ **ไม่ใช่ "แฟล็กเดียว"** กับสถาปัตยกรรม window→last-token ปัจจุบัน
